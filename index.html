02 ・ 置く

S3なんでも置ける倉庫

画像・動画・PDF・CSV・ログ…どんなファイルも保存できるネット上のフォルダ。EC2が「動く場所」なら、S3は「置く場所」です。

中身の構造

my-awesome-bucket   ← バケット（大きな入れ物）
├── images/
│   └── neko.jpg        ← オブジェクト（ファイル）
└── pdf/
    └── catalog.pdf

フォルダに見えるのは、ファイル名に「/」を入れて階層っぽく見せているだけです。

ライフサイクルで自動整理

0日保存よく使う
標準ストレージ
30安い棚へ移動あまり使わない
データ用に自動移動
90自動で削除古いログなどを
自動で片付け

さらに「バージョニング」を有効にすると、上書きしても過去のファイルを残せます。

ここがすごい

消えない（高耐久） どこからでもアクセス 安い（最初は月数円〜） URLで共有 ドラッグ＆ドロップで操作

使い道

WEB画像・CSS・JSの置き場
SITE静的サイトの公開
BKUPバックアップ・ログ
DATAアプリ・IoTのデータ
公開設定のミスに注意
  • 設定ミスでファイルが全世界に丸見えになる事故は実際に起きています
  • 公開するものだけ明確に公開し、それ以外はIAMで制限
まとめ何かを置いてあるところは、だいたいS3。
03 ・ 記録する

RDSおまかせDB屋さん

インストール、バックアップ、障害対応、パッチ適用など、データベースの面倒な管理をAWSが代わりにやってくれるサービスです。

RDS か、EC2に自分でDBを入れるか

RDSEC2＋自前DB
構築・運用の手間 ほぼおまかせ 全部自分で
OSまで触れる自由度 一部制限あり 自由自在
費用 やや高め 抑えられる
バックアップ自動スクリプトやcronで設定
向いている人初心者〜中級者中級者以上

ラクしたいならRDS、全部自分で触りたいならEC2にDBをインストール。

選べるデータベース

MySQLPostgreSQLMariaDBOracleSQL ServerAurora（AWS独自・人気）

つなぎ方

作成すると「エンドポイント」というURLがもらえます。それをアプリに設定するだけ。

mysql -h your-db-endpoint.rds.amazonaws.com -u user -p
よくある注意ポイント
  • 起動しっぱなしで課金され続ける
  • テスト中に「パブリックアクセスON」のまま
  • サイズ選び：小さすぎると遅い、大きすぎるとお金が溶ける

定番の組み合わせ：S3 ＋ CloudFront

静的サイトをS3に置くCloudFront経由で高速配信HTTPS・独自ドメインOKOACでS3への直アクセスを禁止

料金は転送量とリクエスト数の従量課金。無料枠（毎月1TBの転送まで）があるので、小〜中規模ならまず無料で試せます。

注意点
  • キャッシュが効いて古い内容が出続ける → キャッシュ無効化（Invalidation）
  • HTTPSには証明書が必要 → ACMで無料発行
  • 設定項目は多いが、S3＋デフォルト設定なら最小限で始められる

10 ・ つなぐ（土台）

VPC自分専用の土地

Virtual Private Cloud。AWSの中に作る自分だけのネットワーク空間です。EC2やRDSはこの中に置きます。

家にたとえると

どんな時に意識する？

EC2起動時に、どのVPCに置くかを選ぶ
RDS非公開にしたいならプライベートサブネットへ
LambdaDBに接続するなら同じVPCにいる必要あり
よくあるハマりどころ
  • 全部非公開にして外と通信できない

11 ・ 振り分ける

ELBアクセスの交通整理員

Elastic Load Balancing。押し寄せたアクセスを複数のEC2に振り分け、1台にアクセスが集中してパンクするのを防ぎます。

焼肉屋の入口スタッフのように案内する

3つの種類

ALB ・ まずはこれApplication Load BalancerWebアプリ向け。URLのパスで振り分け（/api はA、/image はB）
NLBNetwork Load Balancer超高速。ミリ秒が命のTCP通信向け
CLB ・ 非推奨Classic Load Balancer昔からあるタイプ。古い構成で見かける
気をつけるポイント
  • HTTPS化はELBで（証明書はACMから）
  • セキュリティグループの設定漏れで全ブロック
  • DNS名が *.elb.amazonaws.com になるので独自ドメインはRoute 53と連携
鉄板パターンサーバーを増やす ＝ ELBを入れる。Auto ScalingでEC2を2台→3台に増やしても、URLはそのまま。
12 ・ 土台

リージョン / AZ営業所エリアと独立した建物

リージョンは世界各地にある「データセンターのあるエリア」。AZ（アベイラビリティーゾーン）は、その中にある独立した建物群です。

1つのAZが止まっても、別のAZで動き続ける

リージョンの例

  • 東京ap-northeast-1
  • 大阪ap-northeast-3東京とは別リージョン。東京のAZの1つではありません
  • オレゴン（米国西部）us-west-2
  • フランクフルトeu-central-1
  • バージニア北部（米国東部）us-east-1新サービスはここから先に使えることが多く、東京ではまだ使えない場合もあります

リージョンを選ぶ理由は2つ

障害対策複数AZに分散本番はマルチAZが鉄則
法律・距離置き場所を選ぶ国内保管が必要なら東京、北米向けなら米国

S3など一部のサービスはAWSが自動でAZに分散するので、AZを意識しなくてOK。EC2やRDSはAZ選びが重要です。

BONUS ・ AI開発ツール

Kiro仕様書から作るAI開発パートナー

AWSが提供するAIエージェント型の開発環境（IDE・CLI・Web）。いきなりコードを書くのではなく、まず「要件 → 設計 → タスク」を文書にしてから実装するスペック駆動開発が特徴です。

VIBE MODEチャットでさっと作る

思いついたことを話しかけて、すぐ試作。小さな修正や実験向け。

SPEC MODE仕様書を作ってから作る

要件・設計・タスクを先に固める。本格的な機能や複数人での開発向け。

スペック駆動開発の流れ（例：静的サイトを作りたい）

1promptやりたいことを伝える「S3とCloudFrontで会社のサイトを公開したい」
2requirements.md要件ユーザーストーリーと「何ができたら完成か」の受け入れ条件
3design.md設計構成図、データの流れ、使うAWSサービス
4tasks.mdタスク順番付きの作業リスト。1つずつ実行できる
5code + test実装・テストエージェントがタスクを進め、テストで確認

主な機能

SPECS仕様書づくり

プロンプトから要件・設計・タスクを自動で書き起こす。人がレビューしてから実装へ進める。

HOOKS自動お手伝い

ファイル保存などをきっかけに、裏でエージェントが作業する。

例：保存したらテストを追加、ドキュメントを更新
STEERINGルールを覚えさせる

使う技術、命名規則、チームの決まりごとをファイルに書いておくと、毎回それに従う。

MCP / POWERS外部ツールとつなぐ

MCPでドキュメントやAPI、Terraform・Figmaなどと連携し、より正確に作業できる。

AGENTS任せて並行作業

自律モードやサブエージェントで、大きな作業を分担して進める。

CLIターミナルでも

CLIのヘッドレスモードでCI/CDパイプラインにも組み込める。

この資料の知識が、AIの設計を読む力になる

## 構成
- 静的ファイルは S3 バケットに配置
